## 1. Задача

Нужно было сделать основу системы онлайн-школы: принимать сдачи лабораторных, строго их проверять, хранить как неизменяемые версии и запускать по ним заменяемые анализаторы. Анализаторы в этой работе простые: подсчёт строк и поиск разрешённого шаблона. Код студентов не исполняется, интеллектуальная модель не нужна.

Для AI-траектории дополнительно требовались manifest корпуса, конфигурация режима ML или LLM, интерфейсы подготовки входа и формирования feedback, локальный baseline и stub модели с общим контрактом результата.

## 2. Что сделано

### Этап A. Приём и валидация

| Требование | Реализация |
|---|---|
| Пакет в src-layout | `src/school_lab`, `pyproject.toml`, команда `school-lab` |
| Модель Submission, проверка полей, часового пояса и AI-декларации | Pydantic 2 в строгом режиме: без приведения типов, лишние поля запрещены, объекты неизменяемы |
| Ошибка содержит code, field и message | `SubmissionError`, коды `invalid_json`, `schema_error`, `unsupported_version`, `conflict` |
| Входные данные не меняются | Валидация создаёт новый объект; проверено тестами на каждом ошибочном случае |
| Повтор с тем же хешем — duplicate, с другим — conflict | `SubmissionService.accept`, отпечаток SHA-256 канонического JSON |
| In-memory репозиторий | `InMemorySubmissionRepository`, повторная запись запрещена |
| Импорт не останавливается на ошибочной строке | `import_source` пишет ошибку с номером строки и продолжает |
| AI: корпус и manifest | `build_manifest`: id, хеши, версия обработки `ingestion-1` |
| AI: text и code отделены от признаков, декларация не метка | `preparation.py` строит отдельный payload без `ai_declaration` |
| AI: режим ML или LLM | `configs/llm.toml` (версия шаблона запроса), `configs/ml.toml` (версия схемы признаков) |

### Этап B. Контракты и расширения

| Требование | Реализация |
|---|---|
| Контракт `analyze(submission, context)` → `AnalysisReport` | Protocol `Analyzer`, контекст с заданием и конфигурацией |
| `analyzer_id`, `analyzer_version` в отчёте | Плюс `submission_hash` и `config_hash` |
| LengthAnalyzer | Непустые строки text и code, `rubric_feedback`, `score = null` |
| TemplateAnalyzer | Точные блоки шаблона, `similarity` с пояснением, что совпадение разрешено |
| Номера строк evidence относятся к исходнику | Исходный текст не нормализуется; границы проверяются `validate_report` |
| JSONL и in-memory источники | `JSONLSource`, `InMemorySource` с общим контрактом |
| Файл закрывается при ошибке и досрочном выходе | Контекстный менеджер `open()`, проверено тремя тестами |
| Выбор анализатора без ветвлений по классам | Явный реестр фабрик `AnalyzerRegistry` |
| AI: интерфейсы подготовки входа и feedback | `InputPreparer`, `FeedbackGenerator`, `ModelAdapter` |
| AI: локальный анализатор требований и stub модели | `RequirementsBaseline`, `LocalModelStub`, общий результат `ModelFeedback` v1 |
| AI: фиксированный `config_hash` | SHA-256 от задания и конфигурации режима |
| Третий анализатор без изменения сервиса | `DeclarationAnalyzer` подключён одной строкой регистрации |

## 3. Архитектура

```
JSONL ─► JSONLSource ─► decode_json ─► parse_submission ─► SubmissionService ─► Repository
                         (синтаксис)     (схема)             (duplicate/conflict)
                                                                      │
AnalysisReport ◄─ validate_report ◄─ analyzer.analyze ◄─ AnalyzerRegistry ◄─ AnalysisService
```

Основные решения:

- **Валидация на границе.** Внешние данные проверяются один раз при входе. Внутри системы объекты уже корректны, а прямой вызов конструктора `Submission(...)` тоже проверяет все правила.
- **Контракты через Protocol, а не наследование.** Анализатору не нужно импортировать базовый класс, достаточно нужных атрибутов и метода. Проверку поведения дают контрактные тесты и `validate_report`.
- **Реестр вместо if/elif.** `AnalysisService` не знает ни одного конкретного анализатора. Новый подключается в `app.py`, сервис не меняется.
- **Результат плагина не доверенный.** Отчёт перепроверяется: схема, хеш сдачи, `config_hash`, границы evidence. Ответ модели проверяется до создания отчёта.
- **Домен не знает про CLI.** Сервисы не читают stdin и не печатают. Коды выхода и формат вывода решает `cli.py`, поэтому в ЛР 3 тот же код подключится к HTTP.

## 7. Углублённый уровень

Выбрано углубление AI-траектории:

- одинаковые контрактные тесты для `requirements` (baseline) и `model-stub` в обоих режимах;
- проверка ответа модели до создания отчёта: схема, лишние поля, набор критериев рубрики, ссылки evidence;
- отказ при несовместимой версии схемы ответа (`unsupported_schema_version`).

**Что ловит.** 14 тестовых случаев некорректного ответа: версия 2, `true` вместо версии, неполный ответ, лишнее поле, строка вместо bool, пропущенный или выдуманный критерий, пустое объяснение, неизвестный статус, строка или `null` вместо объекта, ссылка на несуществующую строку. Все отклоняются, отчёт не создаётся.

**Сколько стоит.**

| Операция | Время на вызов, мкс |
|---|---|
| ответ stub-модели | 0.8 |
| `parse_feedback` (проверка ответа) | 4.7 |
| `validate_report` (проверка отчёта) | 20.2 |
| полный запуск `model-stub` через сервис | 78.4 |

Проверка ответа модели занимает около 6% времени анализа. Для настоящей модели, ответ которой идёт секунды, это пренебрежимо мало.

При замере нашлось место для оптимизации. Отчёт проверяется дважды: в `make_report` и ещё раз в `AnalysisService`. Две проверки по 20 мкс — это примерно половина всего времени анализа. Проверка в сервисе обязательна, потому что это граница для сторонних плагинов. Проверку в `make_report` можно убрать для встроенных анализаторов. Сейчас она оставлена намеренно: так ошибка встроенного анализатора видна сразу в месте возникновения, а на текущих объёмах время не критично.

## 8. Ограничения

- Хранилище in-memory: данные живут до конца процесса. 
- Проверка `get` и `add` в репозитории не атомарна между потоками. 
- `template` и `requirements` ищут точные совпадения. Другое форматирование или имя переменной не распознаётся. 
- Stub проверяет программную связку. Замеры на stub нельзя переносить на настоящую модель.
- Анализаторы выполняются с правами процесса. Проверяется их результат, но не их код.
- Размер строки JSONL не ограничивается.
- Синтетический корпус для замеров однородный: реальные сдачи разной длины дадут другой разброс времени.

## 9. Вывод

Основа системы готова и выполняет все требования ЛР 1 для AI-траектории на основном и углублённом уровне. Сдачи принимаются строго: каждая ошибка имеет код, поле и номер строки, а принятая версия не меняется и не перезаписывается. Анализаторы подключаются через реестр, и третий анализатор добавлен без изменения центрального сервиса. Отчёт всегда привязан к конкретной версии сдачи, анализатора и конфигурации.

Проверка ответа модели почти ничего не стоит (около 6% времени анализа) и отсекает весь класс некорректных ответов ещё до создания отчёта. Импорт масштабируется линейно, около 18 мкс на запись. Узкое место по памяти - in-memory хранилище, а по времени - двойная проверка отчёта. Обе вещи понятны и будут затронуты в следующих работах.

Простые методы честно показывают свои пределы: поиск по точному совпадению пропускает другое форматирование, и система в таких случаях передаёт решение преподавателю, а не выносит вердикт.
